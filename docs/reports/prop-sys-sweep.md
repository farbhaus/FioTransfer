## 1. What this sweep covers

The earlier sweep (`tests/prop_*.rs` in the root crate) covered the port. What
landed after it is the C boundary: commit `1d68d8e` ("unsafe: one C-boundary
crate, and the app forbids unsafe code") created `sys/` and made the app
`#![forbid(unsafe_code)]`, so every `&str`/`String`, `libc` and AppKit call in
the app now goes through `fiotransfer-sys`.

**Paths used:** `/tmp/prop-sys/sys/src/{strings,platform,dialogs,quick,services,tray,gui}.rs`
(the `sys/` crate itself, exactly as `origin/main` has it). No extraction was in
flight at that commit, so no substitute path was needed.

## 5. Findings

### F1 — `platform::strerror_text` returns another thread's message for unknown errno codes (**fixed on `consolidate`**)

`strerror` is not thread-safe for codes it does not know: it formats
`"Unknown error: N"` into one process-wide static buffer (`strerrbuf` in
Darwin's libc) and returns a pointer into it. `strerror_text` copies from that
pointer after the call, so two threads asking about two different unknown codes
read each other's answer. Known codes come from a `const` table and are safe.

Evidence (eight threads, seven consecutive unknown codes, 2 000 calls each,
five consecutive runs):

```
assertion `left == right` failed: 8849/16000 answers named the wrong errno
assertion `left == right` failed: 8491/16000 answers named the wrong errno
assertion `left == right` failed: 8661/16000 answers named the wrong errno
assertion `left == right` failed: 8742/16000 answers named the wrong errno
assertion `left == right` failed: 9690/16000 answers named the wrong errno
```

Minimal reproduction: `sys/tests/prop_sys_fs.rs`,
`finding_strerror_text_of_unknown_codes_is_not_thread_safe` (`#[ignore]`d, so the
suite stays green):

```sh
cargo test --offline --test prop_sys_fs -- --ignored
```

```rust
for i in 0..2000usize {
    let code = 300 + (i % 7) as i32;                // seven unknown codes
    assert_eq!(strerror_text(code), format!("Unknown error: {code}"));
}
// run the loop on eight threads: ~55 % of the answers name a neighbour's errno
```

Reachability in the app: `login::os_message` (`src/login.rs:111`) formats the
message for every `io::Error` on the login/CA paths, which the transfer engine
drives from several threads; a user-facing message can name somebody else's
errno. Impact is a wrong message, not wrong behaviour.

Verified repair — **applied on `consolidate`** (it was applied, run and reverted
on this branch, which is why `sys/src` is unmodified here):

```rust
#[cfg(unix)]
static STRERROR_LOCK: std::sync::Mutex<()> = std::sync::Mutex::new(());

#[cfg(unix)]
pub fn strerror_text(code: i32) -> String {
    let _guard = STRERROR_LOCK.lock().unwrap_or_else(|e| e.into_inner());
    let p = unsafe { libc::strerror(code) };
    if p.is_null() { return String::new(); }
    unsafe { std::ffi::CStr::from_ptr(p) }.to_string_lossy().into_owned()
}
```

With that patch: the ignored test passes, the rest of the suite is green, and the
texts for all 5 000 codes in `-1000..4000` are byte-identical to the unpatched
build (so no user-visible change except the fix).

The alternative, `strerror_r` into a caller buffer, was also tried and **rejected**:
Darwin's XSI `strerror_r` returns non-zero for unknown codes, so `-1` and `1000`
would become `""` and every `"Unknown error: N"` message would disappear. (glibc's
GNU variant is a different signature, so a portable version needs two `cfg`
arms — see the note in the patch attempt if it is ever revisited.)

### F2 — `cstr_or_empty` does not turn an interior NUL into a space (behaviour that contradicts the brief)

The brief for this sweep said both constructors turn a NUL into a space. Only
`cstr` does:

| input | `cstr` | `cstr_or_empty` |
|---|---|---|
| `"a\0b"` | `"a b"` | `""` |
| `"\0ab\0cd\0"` | `" ab cd "` | `""` |

`cstr_or_empty` is documented that way in `strings.rs` ("the call is made with an
empty string instead"), so code and docs agree; the brief's assumption was
wrong. Both are pinned by tests, so any change to either is caught. Worth
knowing for the call sites: `gui.rs` uses `cstr_or_empty` for `eval_js`,
`eval_js_to_file` and `snapshot_webview`, so a NUL anywhere in a JS expression
makes the whole script — or the whole snapshot path — empty rather than "mostly
right".

### F3 — a panic in a Rust hook aborts the app (observation, not a defect claim)

`quick::goQuickInspect`, `quick::goQuickDest`, `quick::goQuickStart`,
`services::goService` and `tray::goTrayAction` are `extern "C"` and call the
registered Rust hook directly. Rust 2021 `extern "C"` is non-unwinding, so a
panic in a hook (or in `from_c_str` reached from one) aborts the process instead
of surfacing as an error. Seen for real during calibration: mutation M6 produced
`thread caused non-unwinding panic. aborting.` / `signal: 6` instead of an
assertion failure. Not exercised as a test — a passing test would have to abort.
If the app's hooks can panic (they format strings and touch `&str`s), the
cheap hardening is `catch_unwind` inside the `extern "C"` bodies or
`extern "C-unwind"`.

### F4 — generator lesson: `any::<String>()` never produced a NUL

Measured 0 interior NULs in 400 samples, so the two `cstr*` properties could not
see the NUL branch at all and mutation M9 slipped past them at first. Fixed by
`common::arb_string_with_nul`, which builds the NUL in (400/400, 300 with more
than one) — after which M1 and M9 are caught by the properties as well as by the
pinned test. This is the single most useful calibration result of the sweep: the
properties were green, and green for the wrong reason.

### F5 — environment note: APFS rejects some code points (not a crate bug)

`fs::write` fails with `EILSEQ` ("Illegal byte sequence") for names containing
unassigned code points such as U+3347A or U+10FFFF, even though they are valid
Rust `char`s. Unreachable paths are the honest answer for `is_writable` (false)
and `is_network_volume` (false), which the corpus test checks; the generated
"real file with a mode" property skips the cases the file system refuses.

## 6. What I could not reach

* **Every AppKit shim call**: `open_files`, `open_dir`, `save_file`, `question`,
  `alert`, `clipboard_get`, `clipboard_set`, `window_png`, `menu_init`,
  `window_style`, `snapshot_webview`, `eval_js`, `eval_js_to_file`,
  `tray_init`, `tray_set`, `tray_jobs`, `sync_dock`, `activate`, `set_active`,
  `services_init`, `quick_show`, `quick_info`, `quick_started`. They need a real
  AppKit main thread (some block until a panel closes, some open a browser or a
  Finder window or start a sign-in server). `take_string` is the half of that
  boundary that *is* testable, and it is covered. Only `pre_exec_detach` was
  exercised for real, because a real process is its point.
* **`is_network_volume` returning true.** This machine has no network mount
  (`/sbin/mount`: apfs, devfs, autofs only), so only the false branch and the
  type-name oracle's agreement are checked. The oracle knows the network type
  names, but it never sees one.
* **`sigint_ignored`.** Asking the question resets the process' SIGINT
  disposition to the default, so a test that calls it changes the test harness'
  own signal handling. It would need a re-exec'd child; not done here.
* **`local_time`'s `None` threshold.** There is no documented contract for where
  `localtime_r` gives up (here: `i64::MAX/2` and `i64::MIN` are `None`,
  2⁴⁰ seconds — year 36812 — is `Some`). The suite pins "total, and every `Some`
  is a valid civil reading", not the boundary value.
* **`take_string` on a non-`malloc`ed pointer, or twice**: that is UB by
  construction, so only the "reads once, frees once, frees the same pointer"
  direction is tested.

`sys/src` unmodified. One real defect (F1) with a verified 5-line repair, one
behaviour worth deciding on (F2), one hardening suggestion (F3), and a
31-test suite (1 ignored finding) that runs in half a second.
